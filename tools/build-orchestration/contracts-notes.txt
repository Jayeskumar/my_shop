===== CONTRACT AGENT =====
SUMMARY: Wrote the complete API contracts for sales, payments and purchases in packages/shared/src/api/{sales,payments,purchases}.ts: Zod 4 entity/list/detail/request schemas, a defineRoutes catalogue for every endpoint, and the pure maths both sides need. The cart pricing function priceCart() is shared, so the POS and the server compute identical totals. Each request and response schema has a realistic-fixture test, and a structural test checks all three catalogues. I hardened payment-intent consumption in core/payments.ts recordPayment and added integration tests for it, including a concurrency test. I made one small additive change to the foundation settings.ts (a shift-required flag and register scale/silent-print settings) and updated docs/API.md (my three sections) and ARCHITECTURE §8.4/§12. Writing the tests surfaced one real loyalty edge case: capping by a small bill could leave fewer points than the minimum, which core/loyalty would reject. That case now redeems nothing and reports loyalty_below_minimum. No commits made (the orchestrator made a WIP checkpoint mid-way).
DECISIONS: - **Message keys:** validation messages are snake_case keys exported as SALES_/PAYMENTS_/PURCHASES_VALIDATION_KEYS. This matches the identity agent's convention: the web looks up errors:validation.<key>, then <module>:validation.<key>.
- **Shared helpers:** payments.ts exports the query/body helpers that sales and purchases also use: zQueryList (one value or repeated keys → array), zQueryInt, zIfUpdatedAt, zNullableText, zAmountPaise, zMilli0, zReason, zListFormat, plus the date-range helpers. purchases.ts imports zQueryIds from identity.
- **Import graph:**
  - sales imports payments and parties (loyalty).
  - purchases imports payments, sales (TaxBreakupRowSchema) and identity.
  - payments imports none of the others.
- **List responses:** they are listOf(Row).extend({summary}), and the totals cover the whole filtered range. `?format=csv` on the same list route streams CSV.
- **Pricing contract:**
  - priceCart() runs promotions on undiscounted amounts, then the bill discount (manual bp + flat, then bill promotions, then loyalty; each capped by what is left), then computeDocument. The server resolves catalogue data and calls it; the POS calls it with Dexie data.
  - Default price order (resolveUnitPrice): store price > wholesale tier > batch price > product price. MRP order: batch > store > product.
  - Loyalty redemption is a flat bill discount (part of bill_discount_paise, also reported as loyalty_redeem_paise). It uses the parties helpers loyaltyRedeemIssue / loyaltyValuePaise / loyaltyPointsForAmount, so there is one formula, the same one core/loyalty uses.
- **Quote issues vs create errors:** the quote returns all issues as typed `issues` plus can_complete and requires. Create/complete throws the first blocking one as salesIssueErrorCode(code), with details {reason, line_key, issues}: RX_REQUIRED, EXPIRED_BATCH, INSUFFICIENT_STOCK, CREDIT_LIMIT_EXCEEDED; FORBIDDEN for overrides; FEATURE_NOT_IN_PLAN for credit without khata; UNPROCESSABLE otherwise.
- **FEFO split:** line keys become key, key#2, … (splitLineKey), with a `fefo_split` warning.
- **Tenders (deviation from the spec):** I dropped `tendered_paise`. For cash, `amount_paise` is the cash handed over. allocateTenders applies non-cash tenders first (each must fit the remaining amount), then cash with change. Cash tender payments store the change in notes via cashTenderNotes() / parseCashTenderNotes(), so reprints know it.
- **Payment origin:** there is no DB column, so origin is derived from the client_ref the posting modules MUST pass to recordPayment: `tender:<invoice_id>:<i>`, `cn:<id>`, `dn:<id>` (paymentClientRef / paymentOriginOf). Only origin 'manual' can be cancelled via POST /payments/:id/cancel; anything else is 409.
- **Intent rules in core recordPayment (documented in the module comment and ARCHITECTURE §8.4):**
  - The intent row is locked FOR UPDATE; it must be paid and unused, in the same store; only receipts with a non-cash method.
  - The amount must EQUAL the money received (paid_amount_paise). An intent is never split.
  - Partial application is done with allocations. The unallocated rest becomes the customer's advance, so it needs a customer party; walk-in intent money must be fully allocated. This is new and stricter: I updated two existing tests to match.
  - A customer-bound intent funds only that customer, except pos_sale intents, which may end as a walk-in bill.
  - A client_ref replay must name the same intent (else IDEMPOTENCY_MISMATCH).
  - Errors carry details.reason: intent_used (409), intent_not_paid, intent_amount_mismatch, intent_store, intent_customer, intent_unallocated, intent_method, intent_direction.
- **Permission refinements vs docs/API.md (updated there):**
  - POST /payments/intents/:id/apply needs payments.collect (it creates money, so payments.read was not enough).
  - POST /sales/credit-notes/:id/cancel needs sales.cancel.
  - Backdated invoices need SALES_BACKDATE_PERMISSION = 'sales.cancel'.
  - The credit-limit override needs sales.credit plus credit_limit_override: true, and is audited (as the spec says).
- **Endpoints added beyond docs/API.md (all in the catalogue and docs):**
  - GET /sales/credit-notes/:id/print
  - GET /payments/open-items (FIFO allocation table, used with allocateFifo)
  - GET /public/v1/pay/:reference_code
  - GET /debit-notes/prefill?batch_ids=&store_id=&supplier_id= (matches inventory's purchaseReturnPrefillPath)
  - reorder-suggestions also accepts product_ids (matches inventory's reorderPrefillPath).
- **Renamed parameter:** GET /payments/upi-qr uses provider_account_id instead of vpa_account_id.
- **Estimates:** they are sales_invoices with doc_type 'estimate' and status completed once numbered, then 'converted'; valid_until is stored in due_date. They are listed with `GET /sales/invoices?doc_type=estimate`. The default invoice list excludes estimates and held/draft bills.
- **Returns:** prorateReturnLine works on charged + free quantity. The final return takes the exact remainder; partial returns are capped by what is still uncredited, so amounts stay exact even after a credit note is cancelled. Debit notes use the same function.
- **Settlements and offline returns:**
  - creditNoteSettlementOptions: refunds are capped by refundable_paise (paid and not yet refunded). For adjust_due, any excess over the due becomes the customer's advance, so a walk-in invoice cannot use adjust_due for more than its due.
  - Offline credit notes are numbered at sync (credit notes are numbered per store); /pos/sync processes invoices first, then credit notes, in array order, one transaction each.
- **Bootstrap:** the row shapes match the web Dexie Cached* types; promotions come as {id, data, updated_at}. In delta mode, barcode_product_ids and store_price_product_ids say for which products the barcodes / store prices in the response are complete. Catalog must bump products.updated_at when barcodes or store prices change.
- **Print model:** SalesPrintModelSchema contains no ids or costs, so the public invoice is {document: print model, pay}. It includes the HSN summary, CGST/SGST(UTGST)/IGST rate rows, both amount-in-words strings, a UPI QR for the due, the composition declaration, rx, A4 copy labels and the signatory.

DECISIONS: General conventions
- Route `response` is always the full envelope (dataOf/listOf).
- Collections that are not paginated use `dataOf(z.array(...))`: the category tree, number series, HSN search results and the permission catalogue.
- GET /stock is the one list with an extended envelope: `listOf(StockRow).extend({ totals })`.
- Custom-rule validation messages are snake_case keys. Each file exports its `<MODULE>_VALIDATION_KEYS`. Where a key already exists in the web's errors:validation (phone, gstin, gstin_state, hsn, pin, email, date_order) I reused it; other keys belong in `<module>:validation.*`. Generic min/max/required checks keep no custom message, so the web's zod error map still applies.
- Query arrays use `zQueryIds`, which accepts repeated keys (what the web client sends) or comma lists.
- Every sort uses `sortQuery(...).prefault(default)`, so handlers always receive `{field, direction}`.

Shared helpers (exported from api/identity.ts; the other three contracts import them)
- PATCH-safe nullable fields: `zNullableText`, `zNullablePhone`, `zNullableGstin`, `zNullablePan`, `zNullableEmail`. Missing means unchanged; null or '' means clear. Common's zOptionalPhone/zOptionalGstin would turn a missing field into null and wipe it on PATCH, so I did not use them in bodies.
- Every PATCH has no defaults, accepts optional `if_updated_at` (→ 409 STALE_WRITE) and rejects an empty body with `empty_patch`.
- Also exported: `zIfUpdatedAt`, `zStoreScope` (uuid or 'all'), `zTags` (lower-cased, de-duplicated), `ExportFormatSchema`, CSV helpers (`toCsv`/`toCsvRow` with formula guard and BOM; `parseCsv`/`parseCsvTable`), the import schemas, `documentPath()` / `DOCUMENT_ROUTES` (web links for audit log, ledgers and movements) and `TAMIL_NADU_DISTRICTS`.

Delete semantics
- Categories, brands and tax slab rules: deleted only when unused; otherwise 409 with a hint to deactivate.
- Products, customers, suppliers, doctors and promotions: DELETE returns `{id, result: 'deleted'|'deactivated'}`.
- Stock-transfer cancel always sets status 'cancelled', including drafts; there is no DELETE route.

Imports
- `ImportJobSchema` is shared by products and customers. `dry_run` defaults to true.
- Errors look like `[{row (file line, header = 1), field, code, message}]`.
- GET /imports/:id lives in the catalog catalogue with permission any-of catalog.write / customers.write.

Additions and deviations from docs/API.md (all now documented there)
- New endpoints: POST /users/:id/reset-password (admin reset, no SMS needed on-prem), POST /number-series (customise a series before its first document, e.g. to continue old numbering; unused series are listed with `id: null`), DELETE /products/:id/barcodes/:barcodeId, GET /products/import/template, GET /customers/import/template, GET /doctors/:id.
- GET /stores and /stores/:id are open to any member, for store pickers and transfer destinations.
- Reads of promotions, doctors, customer loyalty and stock transfers need only the read permission; writes are as listed in API.md.
- PATCH /batches/:id accepts inventory.adjust or catalog.write; expiry/mfg changes still need inventory.adjust (enforced by the backend).
- Files upload as `POST /files?purpose=` (multipart, part `file`). FILE_UPLOAD_RULES follows the spec (logo and product_image 2 MB images, prescription 5 MB, import 10 MB), stricter than core FILE_RULES, so the identity route must enforce it. File content needs the bearer token, so the web fetches it as a blob.

Settings and loyalty
- I added `catalog.auto_sku` (default false) and `catalog.sku_prefix` (default 'P') to settings.ts. The spec asks for automatic SKUs and there was no setting for it; `formatAutoSku()` builds the value.
- `SettingsPatchSchema` and `RegisterSettingsPatchSchema` are strict deep-partials derived from the shared schemas. They keep up automatically with the other agent's new register settings (`silent_print`, `scale`). The server must deep-merge and then validate with the full schema.
- Loyalty maths lives in api/parties.ts and is used by core/loyalty.ts and the POS: `loyaltyPointsForAmount`, `maxRedeemablePoints`, `loyaltyRedeemIssue`, `loyaltyValuePaise`.
- `adjustPoints` writes the audit entry `customer.loyalty_adjust` itself; callers must not audit again.
- Reversal rows carry the original document's ref_type/ref_id.

DECISIONS: Conventions:
- Vendor console routes are `licensingRoutes`, built with `defineVendorRoutes`. They are a RouteDef plus `vendor: {capability}` (null = any active staff member) and carry no tenant `permission`.
- Register them with `route(app, def, handler, {config: {auth: 'user'}, preHandler: [staff guard]})`. They are mode cloud and must 404 unless KADAI_VENDOR_CONSOLE is set.
- Capabilities per role are in `STAFF_ROLE_CAPABILITIES`. Partner users must be scoped to their own partner_id in every handler, and only an owner may grant or change the owner and admin roles.

- Errors carry `details.reason` from `LICENSING_ERROR_REASONS` / `ONPREM_ERROR_REASONS`, each with its error code and Tamil/English text. The shop server relays vendor reasons unchanged.

Signed requests:
- Headers X-Kadai-Installation, X-Kadai-Timestamp (unix seconds) and X-Kadai-Signature (base64 Ed25519 over `installationSignaturePayload`).
- The path includes the query string; the body hash is over the raw bytes. Allowed skew is ±600 s, and a signature already seen in that window is rejected; clients re-sign every retry.
- Online activate is also signed, with the new key from the body (proves the shop holds the private key).
- I changed `plugins/body-parsers.ts` to keep `req.rawBody` for `/public/v1/licensing/*` as well as `/webhooks/*`.
